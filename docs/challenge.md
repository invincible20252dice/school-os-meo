# 集客チャレンジ

## 構成

- `/dashboard/challenge`: 7ミッションの実行記録。暦日によるロックなし。
- `/dashboard/challenge/weekly`: 未完了、後日対応、保存済み設定から説明可能な課題。
- `/api/dashboard/challenge`: 認証・承認・校舎アクセスを既存ヘルパーで検証するGET/POST。
- `src/lib/challenge.ts`: 完了条件と状態遷移。UIとAPIの共通仕様。
- `src/lib/challenge-data.ts`: 既存テーブルへの読み取り専用集計。
- `SchoolChallenge`: 校舎ごとに1件。JSON文書のschemaVersionと楽観ロックversionを別管理。

## 既存機能の再利用

サイドメニュー、Supabaseセッション、校舎スコープ、Google設定、アンケート公開URL、口コミ一覧、実績投稿、Instagram同期、順位計測の導線を再利用する。
既存の口コミ・アンケート・設定レコードは更新しない。新機能から外部送信・公開を自動実行しない。

## 記録の意味

DAY1は7項目の確認・修正・後日対応を記録し、後日対応を残課題として維持する。独自の38項目診断・点数は生成しない。
DAY2は写真8カテゴリの手動確認。AI分類ではない。
DAY3は実際の依頼10名、DAY4は開始時に保存した別の追加依頼目標と口コミ対応を記録する。コピー操作は依頼人数に加算しない。
DAY5はGoogleでの公開確認とURLまたは投稿名・日時が必要。下書きだけでは完了しない。
DAY6は保存済み競合計測IDと改善前後の手動記録が必要。計測なしは確認待ちにできる。
DAY7は問い合わせ先・リンク・テストの確認。テスト問い合わせは成果とは別欄。

完了、対応中、後日対応、確認待ち、未着手を区別する。すべて手動の実行記録で、Google側の実行を自動検証した表示にはしない。
開始時の取得可能な数値と完了時のスナップショットを保存する。未取得はnullであり0ではない。
口コミ件数はDBに保存されたGoogle由来データの件数。Google全件同期済みとは断定しない。
新規口コミはGoogle投稿日が確認できる場合のみ集計する。DB取り込み日時を投稿日として代用しない。
回答率は依頼対象者との対応付けがないため未計測。問い合わせは開始日から記録時点までの累計を手動記録する。
Google経由、流入元不明、その他、テストを区別し、クリック数から問い合わせ数を推計しない。
同期投稿はSyncedPost保存分に限定する。競合画面の固定モックは使用しない。

## DAY別達成管理UI (2026-10-02)

- DAY3は依頼数/10名。DAY4は追加依頼目標の達成と口コミ対応を各50%で評価する。DAY5/6は必要な実行記録が揃った1投稿/1改善を評価する。
- 達成率100%とCLEARは別。完了条件を満たした実行記録を保存するとCLEARになる。CLEAR後の再確認で残課題が生じても完了日時・比較スナップショットは維持する。

- 既存の38項目診断マスターは存在しないため、確認済みの既存ミッション項目だけを詳細表に表示する。未取得の成果は未計測とする。
- 今回はDB/API契約・認証・テナントスコープの変更なし。migration追加なし。

検証: `npm run test:ci`、進捗計算・境界値・CLEAR履歴・週次残課題・全7DAYの表示テスト。ブラウザでは本番コンポーネントと明示した検証用データで、保存、再読み込み、7/10名、スマートフォンの横はみ出しを確認する。本番DBにテスト進捗は書き込まない。

## DAY1保存・CLEAR反映の修正

原因は、全項目達成時も理由を必須とするサーバー検証と、保存成功通知の欠落、DAY指定なしの画面が保存直後に次の未完了DAYへ切り替わること。statusの内部値は一貫してCOMPLETEDで、名称の不一致ではない。

- DAY1の全項目達成時は理由を任意とする。残課題あり、確認待ち、延期には引き続き理由が必要。
- 初回CLEARには全項目の回答とS/A項目の達成が必要。B/C項目の後日対応・要改善は理由と残課題を保存してCLEAR可能。達成率とは独立して判定する。
- POSTのDB保存成功後にGETを実行し、そのレスポンスを画面へ反映する。保存したDAYを画面上に保持し、保存ボタン付近に結果を表示する。
- 保存成功後のGET失敗は保存失敗と区別する。古い表示を最新のCLEARと偽らず再取得を促す。校舎切替後の旧POST/GETレスポンスは反映しない。
- 未CLEARの次DAYリンクには未完了の注意を表示する。日付や前DAYの完了による移動制限は設けない。
- schema、migration、既存DBレコードの一括更新なし。

追加検証: PGlite上の既存migrationと実SQLにAPIの永続化操作を接続し、保存前後のdocument・version・完了日時、GET再取得、別校舎不変、重要項目未達時の書き込み拒否を検証。Prisma本体の通信ではなくテスト用SQLアダプターによる検証である。本番DBは接続情報の値を取得できず直接照合できていない。本番データへのテスト書き込みは未実施。

### DAY別の判定

| DAY | 現在の根拠とアクション | CLEAR判定 |
| --- | --- | --- |
| 1 | 未確認・要改善の基本情報を重要度順に最大3件。Google未連携も優先 | 既存の全項目回答とS/Aの解消。B/C残課題は理由を保存 |
| 2 | 未確認・不足の写真カテゴリを最大3件。充足済みは提案しない | 各カテゴリの追加・充足・対象外を手動記録 |
| 3 | 最新の保存済み競合計測の口コミ数中央値との差が10件以上なら10名、1〜9件なら5名。30日以上口コミがなければ5名。中央値以上かつ30日以内の投稿日があれば0名を提案 | 保存した目標人数への依頼を手動記録。0名でも確認記録を保存するまでCLEARにしない |
| 4 | 未返信を最優先。DAY3実行中・完了7日以内は追加依頼0名を提案して重複抑止 | 追加依頼目標と口コミ対応の既存確認。対象なしはDBの未返信0件を検証 |
| 5 | SearchQueryLogの最新保存月・表示回数の大きい最大3語をテーマにする。なし/失敗時は需要根拠のない手動テーマと明示 | Googleでの公開確認とURLまたは投稿名・日時の記録 |
| 6 | 保存済み競合計測を提示して1つ改善を選ぶ。データなし/失敗時は計測準備 | 参照計測IDが対象校舎に存在し、改善前後を記録 |
| 7 | 問い合わせ先・リンク・テストの未確認項目 | 既存の導線確認・テスト記録。テスト件数は成果対象外 |

口コミ数はDB保存分でありGoogle全件取得を保証しない。競合の未取得値を0にしない。最新競合計測1件を使い、キーワード横断で同じ競合を重複集計しない。
新目標は未着手時にユーザーが明示的に適用する。既存DAY3は未適用なら10名、DAY4は既存の開始時目標を維持する。開始済みの目標を再取得のたびに変えない。

### 保存・優先順位・重複抑止

- `challenge-next-actions.ts`が単一のルールエンジン。S/A/B/C順、同順位はDAY順、安定キー順で判定する。新たなAI推論は実行しない。
- TOPは1件、各DAYは最大3件。手動確認・保存済みデータ・手動テーマを区別する。
- `nextActionHistory`には採用した提案のキー・DAY・根拠・優先度・関連画面・提案日時・開始日時・更新日時・完了日時・状態・メモ・操作者を保存する。
- 未着手の画面表示だけではDB更新しない。「この改善を開始する」で初めて提案履歴を保存する。
- 対応中・確認待ち・後日対応は根拠データが消えても残す。同じキーを重複提案しない。
- 完了から7日未満は同じ改善を再提案しない。口コミ依頼はDAY3/4を横断し、投稿はテーマが変わっても7日間抑止する。
- DAY実行記録の保存時、対応する提案履歴も完了へ連動する。未対応の確認項目や過去のCLEARだけでは提案を完了にしない。
- アクション単体の手動完了はDAY CLEARを偽装しない。DAYの必要な証跡は既存フォームで保存する。
- 保存は既存schoolId認可とversion比較更新を通し、POST成功後GETで画面更新する。
