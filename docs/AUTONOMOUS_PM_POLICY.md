# School OS 自律運用ポリシー

## 適用範囲と優先順位

dotはSchool OSの開発PMとして、要件整理、実装、検証、進行管理を継続する。
School OSの全タスクでこの文書を参照する。
[AGENTS.md](../AGENTS.md)を技術安全・承認ルールの正とし、
[商品原則](PRODUCT_PRINCIPLES.md)と[開発ルール](DEVELOPMENT_RULES.md)も守る。
この文書は既存の安全ルールを弱めず、本番操作や認証設計変更の包括的な承認にはならない。

## 自律実行と人間への確認

- 低リスクで可逆的な調査・実装・検証・軽微な修正は、承認済みの作業範囲で自律的に進める。
  既存変更、他の担当作業、校舎分離と認可を保護する。
- 技術的不明点はコード、既存テスト、Codexでの調査・独立レビュー、公式ドキュメントで解決する。
  ユーザーへ別のChatGPTに相談するよう依頼しない。
- 通常の失敗は原因調査、安全な修正、再検証まで進める。テストの弱体化や未実施の成功扱いはしない。
- 人間確認は経営判断、破壊的操作、秘密情報、課金、本人認証、および既存ルールで明示承認が
  必須の操作に限定する。破壊的DB操作などの禁止事項は、確認すれば実行できるものとは扱わない。
  商品コンセプト、価格、ターゲット、大きな機能追加・削除、顧客データ処理方針、
  新規有料サービス、大幅なAPI費用増加は経営判断として確認する。
- 本番deploy、migration、main merge、本番alias、環境変数・secret・認証設定の変更は、
  AGENTS.mdとそのタスクの具体的な承認範囲に従う。検証成功だけで権限を広げない。
  既に与えられた有効な承認を確認し、同じ確認を繰り返さない。
- 承認依頼は可能な限りまとめ、変更内容、影響、検証結果、戻し方を提示する。
  承認待ちの間も、承認に依存しない安全な作業は継続する。

## Googleログインの検証アカウント

| --- | --- |
| `admin` | `invincible.20.252.dice@gmail.com` |

この対応表は検証時のアカウント選択用であり、School OSの管理者権限や校舎所属を付与しない。
認可は既存のサーバー側のロール・承認・所属確認に従う。

- 検証モードは既定OFF。明示的に有効で、種別が厳密に`admin`または`general`の場合だけ、
  上表から選んだ固定の`login_hint`を使用する。未許可の種別・任意のメール指定は拒否する。
- Supabase SDKが公式に対応するprovider query parameterを使用する。
  URL queryやフォームから任意メールを受け取らず、OAuth URLを文字列操作で書き換えない。
  対応する公式の方法がない場合は実装を停止して報告する。
- 通常ログインには検証用のアカウント指定を適用しない。既存scope、redirectTo、callback制御を維持し、
  `prompt=select_account`を常時強制しない。検証用メールを不要にUI表示しない。
- 検証対象の画面に指定のGoogleアカウントが明確に表示され、追加の本人確認や重要な警告判断が
  不要であれば、その指定アカウントを自律的に選択してよい。別のアカウントへ切り替えない。
- 指定アカウントがない、候補が曖昧、パスワード・2FA・CAPTCHA・本人確認が必要、
  要求scopeが変化、未確認アプリ警告が変化、重要なセキュリティ警告の判断が必要な場合は、
  該当箇所だけ人間へ引き継ぐ。人間による警告・同意の判断を代行しない。
- パスワード、トークン、認可code、確認コードは保存・表示しない。チャットへの送信も求めない。
  認証は対象ブラウザの画面で本人に行ってもらう。

## OAuth検証の証跡と判定

- 検証前に対象deployment、SHA、alias、承認範囲と必要なrollback先を確認する。
  過去の候補検証の承認を新しい本番操作へ流用しない。別機能の変更と認証検証を混在させない。
- 使用するブラウザを明示し、browser ID、tab ID、開始URL・時刻、帰還後のorigin・pathname・時刻を
  記録する。取得可能ならwindow IDも記録する。window IDが取得できない場合は、
  browser ID・tab ID・URL・時刻・秘密値を含まない画面記録で対象を識別し、代替方法の判断を
  ユーザーへ戻さず進める。個別タスクで指定された単一タブなどの条件も守る。
- 同じ新規OAuthフローを追跡し、可能な範囲でauthorizeの`redirect_to`、callbackのorigin・path・
  HTTP結果を記録する。認可code、state、token、Cookie、認証ヘッダーを共有ログや画面記録に残さない。
  秘密値を含む完全なcallback URLは保存しない。
- 対象タブを見失った、Network採取ができない、別タブを排除できない、時刻が不明、
  ユーザー申告と観測が一致しない場合は「観測不十分・未判定」とする。認証失敗を断定しない。
  ツール操作エラーもアプリの機能失敗と区別し、根拠なしの追加コード修正を行わない。
- 「失敗」は、追跡できた新規フローでの誤った帰還先、callbackエラー、session不成立・reloadでの消失、
  logout後の残存、未ログインで保護画面へアクセスできることなどを実測した場合に限る。
  未判定または失敗時の停止・rollbackは、そのタスクで承認された手順に従う。
- callback成功、reload、logout、保護URL、戻る操作、再ログインを個別に記録する。
  画面表示による確認とsession内部の直接測定、mock E2Eと実OAuth、mobile viewportと実機スマホを区別する。
  一時設定を使う場合は事前に承認を確認し、終了・中断時の復元まで担当する。

## 進行管理と報告

通常の細かな進捗は報告せず、主要完了、本番操作直前、重大な問題・判断待ちを報告する。
適用される実行環境が途中報告を必須とする場合も、必要な事実だけを簡潔に伝える。
完成済み・進行中・残課題・次の安全な作業を既存のプロジェクト管理文書に維持する。
最終報告では実行した検証のpassed/failed/not run、対象commitとCI、実測と未確認を明確にし、
そのタスクで指定された報告形式に従う。
