# School OS 自律運用ポリシー

## 適用範囲

[AGENTS.md](../AGENTS.md)、[商品原則](PRODUCT_PRINCIPLES.md)、
[開発ルール](DEVELOPMENT_RULES.md)、[検証ルール](testing.md)を補完する。
既存規則を削除・上書き・弱体化せず、実行環境の上位安全規則とユーザーの最新の
具体的指示を優先する。この文書自体は操作の承認を付与しない。

## 自律実行と共通記録

- 現在の有効な承認範囲内で、調査 → TDD → 実装 → test/typecheck/lint/build →
  desktop/mobile E2E → CI → 独立レビュー → 軽微修正 → 再検証を継続する。
  文書だけの変更などでは適用範囲を説明し、既存の `codex:verify` 要件を省略しない。
  失敗は調査・安全な修正・再検証まで担当し、テストを弱体化しない。
- 利用可能なツール、コード、テスト、公式資料と独立レビューで判断する。
  ユーザーに別GPTへの相談、AI間の伝言、スクリーンショットの転送を要求しない。
  ツール不足や本人操作が必須の場合は、その具体的な制約と必要操作だけを報告する。
- PR / Issue / ExecPlan / CI を共通記録とし、対象、受け入れ条件、判断、承認範囲、
  固定した full SHA、証拠リンク、残課題を共有する。既存作業を保護し、
  [ExecPlan](exec-plans/README.md)が必要な変更では既存手順どおり別に作成・更新する。
  外部書き込みが未承認ならローカルに記録を準備し、承認後に共通記録へ反映する。
- 独立レビューは対象SHAと差分を固定し、既存規則・認可・検証証拠を確認する。
  修正後は対象SHAを更新し、影響する検証と必要な再レビューを行う。

## 承認境界

- 既存承認を再利用するのは、同一の対象・操作・環境・条件の有効範囲内に限る。
  同じ確認を繰り返さず、対象・条件・リスクが変われば再判断する。
- PR作成、push、それに伴う自動deployment、main merge、deploy/promote、alias変更、
  DB書き込み・DDL・RLS・GRANT・policy変更、環境変数・secret、課金、認証設定は
  個別の操作として承認範囲を確認する。一つの承認や検証成功から他を推定しない。
- push前に対象ブランチの自動deploymentへの影響を評価する。必要な抑止を確認できず、
  deploymentも承認されていなければpushせず、必要な設定・テスト差分を提示する。
  抑止設定の変更自体も当該タスクの承認範囲に従う。
- 既存禁止を「確認すればできる」と読み替えない。プラットフォームの必須確認、
  安全審査、権限拒否を回避しない。本人認証は実行環境のルールに従う。
- 今回限りのbranch抑止許可、検証アカウント、一時deploymentの許可は、
  恒久権限としてポリシーに保存しない。復元条件がある場合はその条件を守る。
- 本当に必要な承認依頼を集約し、対象・操作・環境・影響・検証結果・戻し方を示す。
  承認待ちでも、依存しない独立した安全な作業は継続する。

## 証拠と報告

- 証拠には対象full SHA、CI URL（未実施ならその旨）、実行環境、時刻と検証範囲を添える。
  実測とmock、成功・失敗・未実施・観測不十分を区別する。
  mock E2Eは実OAuthや本番DBの成功を証明せず、mobile viewportは実機検証と区別する。
- OAuthでは、同じフローのsanitized redirect/callback、deployment SHA・alias、
  観測時刻、browser context（browser/tab ID、取得可能ならwindow ID）を記録する。
  認可code・state・token・secret・Cookie・認証ヘッダーを記録せず、
  秘密値を含む完全URLや画面を保存・共有しない。本人認証情報の転送も求めない。
- タブやフローを追跡できない、必要な観測がない場合は観測不十分とし、認証失敗と断定しない。
  ツール操作失敗と製品の失敗も区別し、推測だけで修正しない。
- 通常の詳細ログは共通記録へ置き、対話での報告は主要成果・必要な承認・重大な問題に絞る。
  実行環境で必須の途中報告と、AGENTS.mdの最終報告項目は維持する。
